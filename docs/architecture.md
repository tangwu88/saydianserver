# 架构与数据边界

## 目标结构

```text
Flutter App / 原小程序
        │
        ├─ V2 /api/saydian-app/v2
        └─ V1 兼容路由
                 │
        NestJS 模块化单体 API
        ├─ 账号 / 会员 / 协议
        ├─ 健康 / 设备 / 关爱
        ├─ 通知 / 内容 / AI / 支持
        ├─ 管理后台 API 与审计
        └─ 商城身份与路由适配 ──> 现有赛电商城
                 │
        PostgreSQL（App 与健康边界）
                 │ 事务 Outbox
        独立 Worker ──> Redis 去重锁 ──> 极光/APNs 适配器
                 │
        私有 S3 兼容对象存储（头像、反馈附件、ECG 压缩文件）
```

## 设计决定

1. 使用模块化单体和独立 Worker。当前吞吐与团队规模不需要微服务，事务边界也更清楚。
2. 健康数据只进入 App PostgreSQL；商品、库存、新订单、支付、物流和售后只进入现有商城。
3. App 账号通过 `CommerceIdentityMap` 与商城 `AppUserIdentity` 永久关联，不使用手机号作长期主键。
4. V1 拼写错误和 multipart 只存在于 `legacy` 模块；V2、数据库和共享类型全部使用规范字段。
5. 手机与手表间的 BLE 指令不进入服务端。服务端只保存绑定、能力快照、固件、在线时间和同步游标。
6. 未知健康值保持缺失；迁移器和 API 均不把未知值补为 `0`。
7. 旧订单只保存不可变投影并合并展示，不进入商城支付、库存或 ERP 流程。

## 模块职责

| 模块 | 主要职责 | 明确不负责 |
|---|---|---|
| `auth` | 注册、登录、短信、刷新轮换、退出、重置、注销申请 | 微信/短信供应商内部实现 |
| `health` | 批量幂等同步、历史、阈值规则、预警事件、ECG 索引 | 诊断、治疗结论 |
| `devices` | 绑定、解绑、能力/固件/游标快照 | BLE 指令与测量算法 |
| `care` | 邀请、授权、撤销、到期、访问审计 | 无授权健康查询 |
| `notifications` | 站内消息、安装实例、未读与多端已读 | 推送载荷中的敏感值 |
| `content` | 百科、协议、AI 会话与供应商适配 | AI 伪回答 |
| `support` | 反馈、客服/更新配置、文件与 ECG 对象 | 公开暴露私有附件 |
| `commerce` | 身份映射、商城路由和旧订单投影合并 | 商品、库存、真实新订单副本 |
| `admin` | RBAC、脱敏查询、内容/协议/反馈/配置与审计 | 未授权原始健康查看 |

## 可扩展点

- 短信使用 `SmsAdapterService`；生产可接受控 Webhook，未配置时返回普通用户提示。
- AI 采用 OpenAI-compatible `/chat/completions` 适配，供应商未配置时不创建伪回复。
- Push Provider 已有 Mock/JPush 边界；APNs 证书缺失时保持禁用。
- 商城只通过受限内部服务令牌调用；后续可替换成 mTLS 或服务网关，不影响 App 合约。
