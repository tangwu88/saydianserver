# 会员编号添加关爱：兼容候选契约

本地候选，未部署。`/global` 是共享 API 内部别名，不是新的账号域。

## 请求与返回

需要有效会员会话。`POST /global/api/saydian-app/v2/care/invitations` 与 canonical 地址相同。

```json
{"memberNo":"29"}
```

`memberNo` 是资料 `memberNo`（旧展示别名 `promo_code`）对应的 `User.compatibilityId`。不是 UUID，不是推广授权或密码。仅接受 `1..2147483647` 的规范十进制字符串，不接受数字、前导零、符号、空格或指数；不能同时提供 `identifier`/`mobile`。

编号模式返回 HTTP 202，沿用统一包裹的 `code:200`，`data` 只有：

```json
{"invitationSubmitted":true}
```

仅表示请求收到，不证明用户存在、通知已送达或健康已授权。通过频控的请求对目标不存在、停用、注销中、已注销或已有关系均不区分返回；不可用目标不创建关系、通知或 Outbox。客户端提示“请求已提交，等待对方确认”；对方接受前，发送方列表不出现该编号邀请。不存在目标不能补造关系。

非法输入 HTTP400；仅编号入口新增账号/目标冷却 HTTP429，`errorKey=CARE_INVITATION_RATE_LIMITED`。账号30秒、目标60秒，均在解析目标/查询已有关系之前预约；目标统一使用规范编号的哈希，不依赖账号存在性。本人通过频控后400；冷却内已知、未知、已有pending/active编号一律429，避免重复202/429构成存在性探测。失败目标也计入冷却，不因失败回滚；冷却后重复pending只确认、不重发通知。本机制不宣称消除所有时序侧信道或替代风控。

邮箱/手机号保持原 `{identifier:...}` 或 `{mobile:...}` 请求、CareRelationship 返回、pending幂等与active重复409；不读写编号预约，不新增这轮账号/目标冷却，原全局频控保留。V1手机号入口不增加编号解析，不把手机号误当编号。该兼容性选择不提供旧联系方式跨入口统一反骚扰保证；新编号是显式增量，不以调用方声称的App身份鉴权。

共用的最小安全差异需单独知晓：非ACTIVE、注销中、已注销联系人现在404，不创建新通知；所有邀请/接受/授权/撤销按关系锁串行；接受时清掉历史pending残余权限。正常ACTIVE联系人邀请节奏与返回契约不变。防止向注销账号继续发通知，以及“接受”自动继承旧权限，是两个入口共同遵守的底线。

## 列表与授权

原 `GET /care/relationships` 的 inviter/recipient 仅增可选 `memberNo`，`id` 仍为 UUID；不增加电话、邮箱或公开会员搜索接口。

新增持久披露态 `identityDisclosure`：旧/联系方式关系默认 `CONTACT`，列表和返回保持原契约；新编号为 `MEMBER_NO_PENDING`，仅收件方可见。对方接受后为 `MEMBER_NO_ACCEPTED`，发送方才可见。未接受而拒绝、撤销、过期仍隐藏；重新编号邀请回到未披露态。已存在联系方式pending/active不因再输入编号隐藏；明确改用已知联系方式重试pending会改为CONTACT，但不重复通知。

V2、V1及 `/global` 列表共用可见性条件；猜测数字关系ID、V2删除不能旁路。V1编号关系只回最小编号/UUID/昵称/头像，不从旧memberContract泄露电话、生日、身高、体重；CONTACT保持旧字段。健康查询继续逐指标拒绝，错误不区分未知账号与没有可用关系。

流程仍为：邀请 → 被邀请方确认 → 被邀请方逐指标授权 → 邀请方按有效关系/指标读取。202、编号存在及 ACTIVE 都不是全量授权。到期、拒绝、撤销和权限关闭仍禁止读取，保留原审计。重邀清除旧权限。

邀请、响应、授权保存和撤销按同一关系事务锁串行；新邀请按账号锁串行。预约复用既有表独立 `care-invite:` 命名空间，不改短信/微信预约；API失败不能伪报请求已接受。

新增 `20261018070000_care_identity_disclosure`：枚举及非空默认CONTACT列，已有行不改变身份/编号/授权。原有已执行SQL和摘要不修改；此迁移只在隔离CI应用，**不加入** `deploy/compatible-migrations.json`。不能合main绕过独立SQL审核、备份恢复演练及生产验收。

### 部署下限候选实现

- `care-privacy-gate.sh` 接入现有统一发布锁和routine失败回退。查验实时API实际数据库/public schema、精确迁移校验值及列/枚举；所有不确定状态失败关闭，不启动旧backup或恢复旧路由。无此迁移、且目标不计划此迁移的原CONTACT库保留正常路径，不增加停止步骤。
- API不可变镜像内运行外部只读行为探针，直接调用其编译后的真实V1/V2控制器与服务，检查确认前隐藏、ID/删除旁路、接受后逐指标及旧CONTACT兼容。Worker核验镜像实际生成的Prisma模型。仅接受镜像ID或受审仓库digest，不使用环境变量、标签或版本号自称兼容。
- 切换和兼容回退均检查唯一发布器、唯一API/Worker、已知数据库连接/网络、非代码覆盖配置及单Node进程。先停止本项目API/Worker，再检查无其他应用数据库会话；迁移后启动前再次排空检查，启动后重新核对实际镜像与拓扑。旧定时器、额外实例、代码挂载和未知客户端均阻断。
- 迁移后不得混跑旧API/旧V1投影。未知或不兼容回退被拒绝后，已进入切换的本项目运行进程保持停止，等待兼容镜像或向前修复，不强行恢复可用性。旧发布/回退入口也使用同一锁并拒绝新披露态库。
- 独立US入口没有本轮单实例协议，故在拉取/切换之前拒绝包含该迁移的清单及已有/未知披露态库；不能借独立旧previous回退绕过下限。无此迁移的旧US路径保留，不宣称US已经支持此功能部署。
- 这会使涉及该迁移的单实例更新有明确停止窗口；实际时长、支付回调重试、生产备份恢复和停写切换仍待独立生产演练，不由CI替代。原业务开关不自动打开；不运行seed，不改变或清理用户数据。
- 新增部署证据只保存脱敏的必要元数据；数据库密码、无关环境变量、挂载来源和进程参数不复制进新证据文件或日志。

远端CI将验证真实镜像行为、历史旧API/旧V1负控、实际镜像HTTP新旧地址，以及合成CONTACT旧数据升级/恢复、部分DDL/查询失败和在途会话。CI容器和合成数据不是生产演练。
