# 旧数据迁移与切换手册

## 绝对边界

- 旧库只允许新建的最小权限只读账号；不使用历史文档中的 root/SSH 密码。
- 首次盘点只读取 `information_schema` 的表、列和估算行数，不读取密码、Token 或健康内容。
- 手机号和微信 UnionID 仅作冲突辅助；旧会员 ID 是永久映射主键。匹配到现有账号时进入人工队列，禁止自动合并。
- 旧订单只导入 `LegacyOrderProjection`，绝不重放支付、库存、ERP 或物流写入。
- 任何清理、旧库删除或附件删除均不属于迁移脚本权限。

## 1. 盘点

1. 复制 `apps/migrator/migration-map.example.json` 到任务外的受控路径。
2. 根据只读结构填写真实表列；不要把真实库名、主机、账号或样例数据提交 Git。
3. 配置 `LEGACY_DATABASE_URL`、`DATABASE_URL`、`MIGRATION_MAP_PATH`、不可覆盖的报告路径。
4. 执行 `pnpm.cmd migrate:inventory`。
5. 由两人复核：字段语义、时间时区、密码算法、会话形式、附件根目录、订单金额单位和 ECG 存储方式。

当前通用迁移器已实现会员、兼容 bcrypt、冲突队列、健康记录、幂等映射与数量/首尾 ID 核验。关爱、消息、内容、AI、地址、订单投影和附件必须在真实只读盘点后补充并锁定对应映射；在此之前不能假报“全量迁移可执行”。

## 2. 脱敏演练

```powershell
pnpm.cmd migrate:import
pnpm.cmd migrate:verify <runId>
```

- 每轮使用新的 `MigrationRun`；`LegacyIdMap` 使重复执行跳过已完成行。
- 无法映射的会员、未知指标、非法时间/JSON、内联 ECG 波形进入 `MigrationConflict`。
- 报告使用 `flag=wx` 创建，不覆盖既有报告；报告作为发布证据单独归档。
- 核验至少包含每表数量、冲突数、首尾 ID、健康指标分布、最早/最晚时间、订单金额、附件数和 SHA-256。

## 3. 正式迁移

1. 建立 PostgreSQL 加密备份和恢复演练证据。
2. 在旧服务继续运行时完成全量迁移。
3. 人工处理冲突队列并重跑核验。
4. 维护窗口开始后暂停旧服务写入，记录准确时间点。
5. 执行最终增量迁移和全量核验；任一总数/金额/附件哈希不一致即停止。
6. 新服务保持 `MAINTENANCE_READ_ONLY=true`，验证登录、健康历史、关爱、旧订单和附件。
7. 通过后才开放新写入并保留切换日志。

## 4. 回滚

- 应用回滚使用上一个不可变镜像标签；数据库迁移只允许向前修复，不自动执行破坏性降级。
- 业务回滚时新服务重新只读，导出维护窗口后的切换日志，按审核后的回放程序处理。
- 旧服务保持只读 14 天，旧数据库和附件不删除。
