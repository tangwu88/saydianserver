## 追加：三个普通商城实际缺陷

- 主任务明确分配修复库存骤降后的购物车减量、提交前报价变化确认与订单状态响应竞态。继续核对 fetch，HEAD/远端仍为上述基线；保留所有在途修改和 ERP 文件。
- 购物车原数量为 5、最新库存为 2 时，点击减号不再先提交无效的 4，而是缩减到当前可用的 2。库存为 0 不发送零数量更新，提示缺货并保留删除入口；正常加减和单次请求互斥保持。
- 查明 `CommerceStoreService.createOrder` 没有报价版本/期望金额输入，事务内重新计算。前端在每次普通提交前对比已展示报价与最新 preview 的价格、券/积分、运费、实付和行分摊；有变化时只更新展示，不写入草稿或请求键，按钮改为“确认新金额并提交”。用户再次提交且报价未再变化才创建订单。提交过程中禁用金额相关编辑，避免展示与参数发生变化。
- `uncertain` 冻结恢复优先于报价比较，继续使用原 key 和原 payload；即使当前价格已变化也不对结果未知的请求重新报价或生成新键。
- 订单列表为每次加载增加请求序号，旧成功/失败响应均不能覆盖新状态标签；离页时使请求失效，回来重新加载。当前加载失败保留错误与重试，不伪装为“当前没有订单”。
- 新增 9 项行为级测试，执行真实页面脚本：库存 5→2、零库存、正常加减/防重复；报价变化第一次暂停/第二次确认、现金总额未变但金额分配变化、再次变价、超时后原键恢复；订单乱序成功/失败、当前错误重试、隐藏/卸载后回填拒绝。
- `pnpm test:h5:flows`：52/52 通过；`pnpm --filter @saydian/app-shop typecheck` 通过；`pnpm --filter @saydian/app-shop test`：42/42 通过（包含主任务同期 8 项分类/搜索测试）；`git diff --check` 通过。未运行构建、提交、部署或真实交易。
- 限制：本次 UI 二次确认覆盖“提交前重新报价发现变化”。最终 preview 和创建事务之间的价格再变化，当前服务端没有条件报价契约，不能声称完全锁价；若要求绝对成交金额确认，需后续增加服务端报价版本/期望金额条件。本次未扩大 API 范围。

## 追加：严格报价条件及并发恢复（上述报价小窗口现已修复）

- 主任务明确要求立即补齐 API 条件报价，不保留已知静默变价窗口。新增 `commerce-quote.ts`；`preview.quote.fingerprint` 为 q1 前缀 SHA-256，固定包含规则版本、商品金额、券/积分/运费/现金及按 SKU 排序的数量、单价、总价和行分摊，排除名称/图片/未使用余额等非成交内容。
- 创建订单新增可选 `expectedQuote`，格式无效返回 400；带条件时，在 Serializable 事务重新报价后、首次订单/积分/券/库存/购物车写入前比较，不同返回 `409 quote_changed`。H5 新单必须携带实际服务端凭据；缺失则拒绝新建，不弱化到无条件请求。既有客户端和旧冻结草稿不带新字段保持兼容；原 requestHash 在字段缺省时不变。
- H5 草稿指纹纳入 expectedQuote。已明确拒绝的变价请求重新报价并二次确认；结果未知继续原键、原字段冻结恢复，不改成新单。
- 独立复核发现同键并发外部查回 miss 的恢复风险，进一步加事务第一条非阻塞 PostgreSQL advisory lock（仅以该订单幂等键哈希为范围）。同键仍处理中返回 `503 order_in_progress`，H5 保持 uncertain；持锁后再查原单，事务失败后再查已提交赢家并校验归属/原请求 hash，避免晚到的报价/券/积分错误把已创建订单误判为未创建。
