# 商城订单下单人和下单方式

- 用户要求总后台订单区分自己下单和代理下单。Start-Change 在干净main安全同步，基线ceb8ece24e57ec5241c208828f6aed131740cfa4；已读AGENTS、handoff及最近库存/下载页记录，独立分支codex/order-purchaser-20261020。
- 原订单API已包含partner名称与伙伴编号，前端“买家”只读user，导致伙伴采购显示未命名会员。改为“下单人”，显示会员下单/品牌伙伴下单标签、实际账户姓名、伙伴编号或原掩码电话；详情补充同一身份及编号，与收货人分开。
- 使用订单userId/partnerId及对应关系，不以VP订单前缀、收货人、会员推广归属推断；会员关联伙伴仍是会员下单，历史缺失或冲突身份明确显示未知/待核实。不会重新指定订单主体、追溯修改交易或推测代客操作。
- 订单搜索补充现有伙伴名称和伙伴编号条件，沿用分页、状态、统计与会员电话脱敏。无新个人字段、迁移、权限或支付逻辑变更，不操作真实订单。仅更新中国站，发布消息保留[deploy cn only]。验证及发布结果续记。
- 用户继续指出详情顶部需单独一行下单人、总后台需点击获取ERP状态/操作日志，伙伴列表、发货处理和物流为空与下方已发货日志不一致。一并实现，保留原请求。原因：处理日志独立同步，erpStatus未从订单查询更新，查询成功后前端也未重新读取包裹；截图中的ERP消息提示未配置物流回调，本轮不修改供应商后台，采用主动查询兜底。
- 共用订单ERP快照与每分钟幂等任务，后台GET只读缓存、POST由超级管理员/商城运营排队并审计；伙伴processing沿用已有受保护GET同步方式，查询始终按partnerId限定。共享订单状态、日志和同步时间，不再从日志文字或订单前缀猜状态。
- Worker用聚水潭官方orders.single.query查询当前订单：按原店铺、线上单号、ERP内部单号严格核对、完整分页；再获取order.action.query日志。全部成功后CAS与事务保存状态/日志；只有实际Sent且返回真实运单号才导入包裹、推进已付款/待发货订单。售后、退款、取消和签收终态不覆盖。失败不替换成功缓存，不改变金额、库存、支付、退款或外部ERP订单。复用已有表，无迁移。
- 参考官方接口 https://open.jushuitan.com/document/2125.html （so_ids数组、ERP状态、l_id/logistics_company/send_date），以及现有日志契约。web首次打开超时，官方页面经只读HTTP取得并核对字段；不采用第三方转载。运单与真实物流轨迹分开，未返回轨迹不编造。界面最多展示最近300日志并明确截断，未知状态保留原值。
